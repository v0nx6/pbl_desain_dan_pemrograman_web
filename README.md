# Boutique NC: Next.js, Prisma, and FASHN Virtual Try-On

A full-stack boutique app for an Indonesian shop selling kebaya, batik, and
tenun. The UI keeps the **Warm Ivory** visual direction. The app is in Indonesian
and includes a real, server-side integration with the official **FASHN VTON v1.5**
Hugging Face Space.

## Stack

| Layer | Choice |
|---|---|
| Framework | Next.js 16 (App Router, Route Handlers, Server Components) |
| UI | React 19, Tailwind CSS 4, custom Warm Ivory tokens |
| Database | PostgreSQL 18 + Prisma 6 |
| Validation | Zod 4 |
| Auth | Opaque session cookies, SHA-256 token hashes, scrypt passwords |
| Try-on | FASHN VTON v1.5 on Hugging Face (Gradio queue API, no local GPU) |
| Fonts | Manrope (single type family for display and body) |
| SEO | Metadata API, JSON-LD, `robots.txt`, `sitemap.xml`, OpenGraph/Twitter |

## Features

### Storefront and customer account

- Catalog with collection filters (`baru`, `batik`, `kebaya`, `priya`) plus
  shopper filters for size, single or couple, price range, best seller, and new
  products. The `priya` collection includes three men's pieces: a batik
  parang shirt, a linen koko shirt, and a tenun blazer. Product detail, size/stock selection, cart, checkout, QRIS,
  bank transfer (BCA, Mandiri, BNI, BRI), or COD payment, payment proof
  upload, and an order timeline.
- Checkout chooses between courier delivery and picking the order up at the
  store. Pickup orders have no shipping cost.
- Registration, login, logout, Google sign-in through Firebase, and session
  cookies.
- **Password reset with email OTP** at `/lupa-sandi`: the customer enters an
  email, receives a 6-digit code, verifies the code, then sets a new password.
  A successful reset signs out every old session. In development without SMTP
  credentials the code is printed in the server log and shown on the reset
  screen so the flow can still be tested.
- **Signup address details**: name, email, password, phone number, street
  address, and an optional address description.
- **Integrated OpenStreetMap preview**: the customer searches for a location,
  sees it on the map, and still types the full address. The map link is
  generated by the server, so there is no URL field to fill and no API key is
  needed.
- **Profile CRUD** at `/akun/profil`: update name, email, phone, shipping
  address, and address description; clear the address; change password; delete
  the account; and open the chat from a shortcut button. Account deletion
  anonymizes the profile but keeps order history for the admin.
- Checkout prefills the saved phone and address.
- **Product reviews** at the bottom of each product page: 1-5 stars, an
  optional comment, and up to three photos. Reviews are separate per product,
  require a logged-in account, and allow one review per customer per product.

### Admin back office

- Live dashboard with revenue, pending verification, active product, and open
  order counts.
- Order list and detail pages, payment verification, status transitions,
  cancellation, and an order timeline.
- **Product create/edit/deactivate** with a real image-upload form. The admin
  does not type a filesystem path. Product fields include size and stock,
  single or couple category, price, best seller, and new product.
- **Product filters** on `/admin?view=produk`: size, single or couple, price
  range, best seller, and new product.
- **Site image management** at `/admin/gambar`: replace the three rotating
  homepage photos and the story photo, or restore the bundled defaults.
- Product and site photos are validated (JPG/PNG/WebP, max 5 MB), stored under
  `.data/products/`, served through `/api/product-image/[name]`, and deleted
  when replaced.
- Admin order/product pages refresh automatically so new customer orders appear
  without a manual reload.
- **Financial recording** at `/admin/keuangan`: create, edit, and delete manual
  income or expense entries with a category, description, amount, and date.
  The page shows manual cash-flow totals, a manual balance, and verified order
  revenue kept separate so the same sale is not counted twice.
- **Revenue CSV export** from `/admin/keuangan`: downloads every verified order
  (paid, processing, shipped, completed) with order number, date, customer,
  payment method, fulfillment, status, subtotal, shipping, and total.

### AI Virtual Try-On

- The customer uploads a full-body photo (JPG/JPEG/PNG/WebP, max 8 MB), sees a
  preview, can replace or remove it, then picks an eligible catalog product.
- The primary action is exactly **“Generate Virtual Try-On”**.
- The result screen shows the generated image, an estimation note, retry,
  download, and return-to-selection controls. Errors are specific and readable.
- Duplicate submissions are blocked on the client and rate-limited on the server.

## How the FASHN integration works

1. The browser posts `multipart/form-data` to `POST /api/try-on` with the photo
   and `productSlug`.
2. The route handler validates the same-origin request, the session, MIME type,
   size, and per-user rate limit.
3. Only products explicitly marked for try-on are accepted. `Product.tryOnPhotoType`
   is `model`, `flat-lay`, or `null`; fabric-detail photos are marked `null` so
   they are never sent to FASHN.
4. `src/lib/tryon.ts` converts both images to base64 data URLs and calls the
   official Space queue:
   - `POST https://fashn-ai-fashn-vton-1-5.hf.space/gradio_api/call/try_on`
   - `GET  .../gradio_api/call/try_on/{event_id}` (Server-Sent Events)
5. Category mapping: `upper_body → tops`, `lower_body → bottoms`,
   `dresses → one-pieces`.
6. The returned image URL is restricted to the Space host and downloaded
   server-side. The generated result is stored in `.data/results/`; it is served
   only to its owner through `/api/try-on/[id]/image`.
7. **The customer photo is never written to disk.** `TryOnJob.photoPath` stays
   `null`; the photo only lives in memory for the request.
8. Provider failures map to safe responses: timeout (504), free-quota/rate limit
   (429), unavailable/sleeping Space (503), rejected image (422).

The Space is public, so `HF_TOKEN` is optional. When present it is read only on
the server and is never exposed to the browser.

## Getting started

### Requirements

- Node.js 20 or newer
- PostgreSQL 16+ (PostgreSQL 18 is used here), or Docker

### 1. Environment

```bash
cp .env.example .env
```

Fill these values in `.env`:

```dotenv
POSTGRES_USER="boutique"
POSTGRES_PASSWORD="choose-a-local-password"
POSTGRES_DB="boutique"
DATABASE_URL="postgresql://boutique:choose-a-local-password@127.0.0.1:5433/boutique?schema=public"
APP_URL="http://localhost:3000"
ADMIN_EMAIL="admin@example.com"
ADMIN_PASSWORD="choose-an-admin-password"
CUSTOMER_EMAIL="customer@example.com"
CUSTOMER_PASSWORD="choose-a-customer-password"
```

`ADMIN_PASSWORD` and `CUSTOMER_PASSWORD` are required by the seed script;
there are no fallback passwords in the source. Optional variables are listed
below.

### 2. Database and seed

```bash
npm install
docker compose up -d        # only if you use the bundled PostgreSQL
npx prisma db push
npm run db:seed
```

The seed resets the seeded products and stock, but keeps users and orders. It
creates the admin and customer accounts from your `.env` values.

### 3. Run

```bash
npm run dev                 # development, http://localhost:3000
# or
npm run build
npm start                   # production build
```

For multi-instance deployments, mount a writable persistent volume at
`DATA_DIR` (default `./.data`).

## Password reset email (Gmail SMTP)

Password reset sends a 6-digit one-time code by email through Gmail SMTP. The
code is stored only as a scrypt hash, expires after 10 minutes, allows five
wrong attempts, and can be used once.

### Gmail setup

1. Open the Google Account for the sender address.
2. Enable **2-Step Verification** under **Security**. App passwords require it.
3. Open `https://myaccount.google.com/apppasswords`, create an app password for
   "Mail", and copy the 16-character value.
4. Put the Gmail address in `GMAIL_USER` and the app password in
   `GMAIL_APP_PASSWORD`. Do not use the normal Gmail password.
5. Optionally set `MAIL_FROM`, for example
   `Boutique NC <toko@example.com>`. It must be a sender the account may use.

Leave both values empty in development to print the OTP to the server console
and show it on the reset screen instead of sending mail. In production, a
missing configuration returns HTTP 503 so a reset is never silently lost.

### Reset flow

1. `/lupa-sandi` sends the email to `POST /api/auth/forgot/request`. The reply is
   always generic, so the form does not reveal which emails are registered.
2. `POST /api/auth/forgot/verify` checks the code and sets a short-lived
   HttpOnly `boutique_reset` cookie.
3. `POST /api/auth/forgot/reset` saves the new password, deletes all sessions
   for that account, and clears the reset cookie.

## Google sign-in with Firebase

Google sign-in uses Firebase Authentication. Firebase runs the Google flow, the
server verifies the Firebase ID token with the Admin SDK, and the app then
creates its normal session cookie. Products, orders, and finance data stay in
PostgreSQL.

### Firebase console setup

1. Open `https://console.firebase.google.com` and create a project.
2. Open **Project settings > General > Your apps** and add a **Web app**.
3. Copy the web app config values into the `NEXT_PUBLIC_FIREBASE_*` variables.
4. Open **Authentication > Sign-in method**, enable **Google**, and choose a
   support email.
5. Open **Authentication > Settings > Authorized domains** and make sure
   `localhost` is listed. Add the staging or production domain later.
6. Open **Project settings > Service accounts**, click **Generate new private
   key**, and download the JSON file.
7. Copy `project_id`, `client_email`, and `private_key` from that JSON into
   `FIREBASE_PROJECT_ID`, `FIREBASE_CLIENT_EMAIL`, and
   `FIREBASE_PRIVATE_KEY`. Keep the quotes around the private key and write the
   line breaks as `\n`.

Leave the Firebase values empty to keep the Google button hidden. Email and
password login still works without Firebase.

### How the login flow works

1. The browser signs in with the Firebase Google provider.
2. The browser sends the Firebase ID token to `/api/auth/firebase`.
3. The server verifies the token, checks that the email is verified, and only
   accepts the `google.com` provider.
4. The server finds the account by `firebaseUid`, links an existing account by
   verified email, or creates a new customer with no password.
5. The server creates the usual opaque session cookie.
6. New Google users without a phone or address are sent to
   `/akun/profil?lengkapi=alamat`.

Google-only accounts can set a password later from the profile page. Until then
they cannot log in with email or delete the account with a password.

## Privacy and security notes

- Customer try-on photos are not persisted anywhere.
- Generated results and payment proofs are stored on local disk and guarded by
  session/ownership checks (or admin role).
- Uploads are validated by MIME allowlist and size, stored under generated UUID
  filenames, and never use a client-supplied path.
- Admin image paths are generated by the server (`/api/product-image/<uuid>.<ext>`).
- Sessions use random opaque tokens; only their SHA-256 hashes are stored.
- Passwords use scrypt with a per-password salt.
- Route handlers enforce same-origin checks for state-changing requests.
- The try-on endpoint is limited to 10 requests per minute per user in memory.

## Map setup

The address preview uses OpenStreetMap tiles and Nominatim search through the
`/api/geocode` route. Neither needs an API key. The route caches lookups for 24
hours and throttles requests to respect the public usage policy. For a
high-traffic deployment, point `NOMINATIM_URL` at your own Nominatim instance.

## Known limits

- The free Hugging Face Space can sleep or throttle; the UI reports this instead
  of faking a result. `FASHN_TIMEOUT_MS` may need lowering to `55000` on hosts
  with a 60-second request cap.
- Payments are simulated. QRIS contains `BUKAN-PEMBAYARAN-NYATA`; bank transfer
  uses a virtual account with a bank prefix. COD orders skip proof upload
  and become paid when the admin marks them complete.
- Chat is local and labeled `Contoh data`.
- Rate limiting is in memory per process; a multi-instance deployment needs a
  shared store.
- Uploads and results need a persistent volume or object storage in production.
- Auth uses email and password plus Google sign-in. There is no MFA yet.
